# BluePay Gateway Bot v0.5.0

بلوپی یک زیرساخت واسط پرداخت مستقیم برای ربات‌ها، وب‌سایت‌ها و چند فروشگاه مستقل است. سامانه فاکتور صادر می‌کند، مبلغ یکتا می‌سازد و پرداخت را با پیامک بانکی تطبیق می‌دهد.

## تغییرات نسخه 0.5.0

- ثبت چند فروشگاه زیر یک حساب پذیرنده
- ایجاد خودکار کد مستقل برای هر فروشگاه
- صدور چند کلید API برای هر فروشگاه
- امکان فعال یا غیرفعال‌کردن هر کلید بدون اثر روی کلیدهای دیگر
- Callback و Secret امضای مستقل برای هر فروشگاه
- امکان تست Callback هر فروشگاه از داخل ربات
- اتصال خودکار هر فاکتور API به فروشگاه و کلیدی که آن را ساخته است
- جداسازی دسترسی: کلید یک فروشگاه نمی‌تواند فاکتور فروشگاه دیگر را استعلام یا لغو کند
- پشتیبانی از تکرار `order_id` یکسان در فروشگاه‌های مختلف
- انتقال خودکار کلید API قدیمی به یک «فروشگاه اصلی» بدون باطل‌شدن کلید
- حفظ Callback عمومی حساب به‌عنوان مسیر سازگاری برای اتصال‌های قدیمی
- نمایش شناسه فروشگاه و کلید در پاسخ API و Callback پرداخت

## ساختار فروشگاهی

```text
حساب پذیرنده
├── فروشگاه اول
│   ├── کلید API سایت
│   ├── کلید API ربات
│   └── کلید API محیط تست
└── فروشگاه دوم
    ├── کلید API سایت
    └── Callback و Secret مستقل
```

هر پذیرنده می‌تواند حداکثر ۲۰ فروشگاه و هر فروشگاه حداکثر ۱۰ کلید API فعال داشته باشد.

مسیر مدیریت:

```text
اتصال و API ← فروشگاه‌ها و APIها
```

هنگام ثبت فروشگاه، اولین کلید API به‌صورت خودکار صادر می‌شود. کلید کامل فقط همان یک‌بار نمایش داده می‌شود.

## نصب روی Railway

فقط دو متغیر لازم است:

```env
BOT_TOKEN=توکن ربات تلگرام
GITHUB_TOKEN=توکن Fine-grained گیت‌هاب با دسترسی Contents: Read and write
```

در اولین اجرا، سامانه Repository و Branch را تشخیص می‌دهد، دیتابیس SQLite و Secretهای داخلی را می‌سازد و نسخه رمزنگاری‌شده دیتابیس را در شاخه `gateway-data` نگه می‌دارد.

## مدیریت کارمزد

مسیر مدیریت پیش‌فرض‌ها:

```text
مرکز مدیریت سامانه ← پیش‌فرض‌های کارمزد
```

- مبلغ صفر به‌معنای کارمزد رایگان است.
- پذیرنده‌های جدید از پیش‌فرض همگانی ارث می‌برند.
- تنظیمات را می‌توان فقط برای یک پذیرنده یا به‌صورت سراسری اعمال کرد.
- فاکتورهای قبلی با تغییر کارمزد دست‌کاری نمی‌شوند.

## قابلیت‌های اصلی

- صدور فاکتور دستی و API

- مبلغ یکتای پرداخت برای جلوگیری از تداخل تراکنش‌های هم‌مبلغ
- چند کارت مقصد برای هر پذیرنده
- کیف پول کارمزد و شارژ آنلاین خودکار
- کارمزد اختصاصی، همگانی یا رایگان
- وبهوک اختصاصی پیامک برای هر پذیرنده
- تشخیص بانک و مبلغ از پیامک‌های بانکی

## تنظیم SMS Forwarder

```http
POST /webhooks/sms/{merchant_id}/{unique_token}
Content-Type: application/json
```

```json
{"device_id":"phone-1","sender":"{in-number}","message":"{msg}","received_time":"{time}","incoming_sim":"{in-sim}"}
```

متغیرهای داخل آکولاد باید با دکمه `{}` خود برنامه SMS Forwarder درج شوند.

## API فروشگاهی

هر کلید API به یک فروشگاه متصل است و فروشگاه از روی کلید تشخیص داده می‌شود؛ نیازی به ارسال `store_id` در بدنه نیست.

ساخت فاکتور:

```http
POST /api/v1/invoices
X-API-Key: gw_xxx
Content-Type: application/json
```

```json
{
  "amount_toman": 200000,
  "order_id": "ORDER-1001",
  "description": "اشتراک یک‌ماهه",
  "fee_mode": "split",
  "ttl_minutes": 30
}
```

پاسخ شامل این اطلاعات فروشگاهی نیز هست:

```json
{
  "store_id": 12,
  "store_code": "ST-A1B2C3D4",
  "store_name": "فروشگاه اصلی",
  "api_key_id": 31
}
```

استعلام و لغو فقط با یکی از کلیدهای همان فروشگاه مجاز است:

```http
GET /api/v1/invoices/{payment_id}
POST /api/v1/invoices/{payment_id}/cancel
X-API-Key: gw_xxx
```

## آپدیت از داخل ربات

مدیر فایل ZIP نسخه جدید را برای ربات ارسال می‌کند. بسته باید حداقل شامل موارد زیر باشد:

```text
Dockerfile
requirements.txt
release.json
app/main.py
```

فایل‌های `.env`، دیتابیس و کلیدهای محرمانه نباید داخل ZIP قرار بگیرند.
