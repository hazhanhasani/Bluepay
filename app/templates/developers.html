HEADERX-API-Key: gw_your_private_key
هر فروشگاه یک کلید API مشخص دارد. کلید فروشگاه دیگر امکان استعلام یا لغو فاکتورهای این فروشگاه را ندارد. کلید را فقط در Backend نگه دارید.
برای تست بدون جابه‌جایی پول از مسیرهای مستقل /api/v1/sandbox استفاده کنید. همان API Key فروشگاه معتبر است، اما داده‌ها، فاکتورها و Callbackها با برچسب sandbox جدا ثبت می‌شوند.

مقادیر مجاز fee_mode

این فیلد مشخص می‌کند چه مقدار از کارمزد تأیید به مبلغ پرداختی مشتری افزوده شود. کارمزد سرویس در زمان ساخت فاکتور از کیف پول پذیرنده رزرو و پس از پرداخت از همان کیف پول کسر می‌شود.

merchantکارمزد کامل از کیف پول پذیرنده رزرو و پس از تأیید کسر می‌شود؛ مبلغی بابت کارمزد به مشتری افزوده نمی‌شود.
customerکارمزد کامل همچنان از کیف پول پذیرنده تسویه می‌شود، اما همان مقدار روی مبلغ پرداخت مشتری افزوده می‌شود؛ customer_fee_rial = fee_amount_rial.
splitنصف کارمزد روی مبلغ مشتری افزوده می‌شود و نصف دیگر بر عهده پذیرنده می‌ماند؛ customer_fee_rial = floor(fee_amount_rial / 2).
defaultتنظیم پیش‌فرض حساب پذیرنده را اعمال می‌کند. حذف فیلد یا ارسال null نیز دقیقاً همین رفتار را دارد.
freeمقدار مجاز API نیست. رایگان‌بودن فقط زمانی فعال است که مدیر کارمزد حساب را روی صفر قرار داده باشد؛ پذیرنده نمی‌تواند با پارامتر درخواست، کارمزد را دور بزند.
اگر مبلغ کارمزد حساب روی صفر باشد، فاکتور بدون رزرو یا کسر کارمزد ساخته می‌شود. در پاسخ فاکتور، fee_amount_rial و customer_fee_rial برابر صفر خواهند بود.
payable_amount_rial = base_amount_rial + customer_fee_rial + unique_amount_rial

Idempotency و جلوگیری از ساخت تکراری

HEADERIdempotency-Key: order-1001-create

برای تمام درخواست‌های ساخت فاکتور Live و Sandbox یک کلید یکتا ارسال کنید. تکرار همان کلید با همان بدنه، پاسخ ذخیره‌شده را با هدر Idempotency-Replayed: true برمی‌گرداند؛ استفاده از همان کلید با بدنه متفاوت خطای 409 ایجاد می‌کند.

کلید باید بین ۸ تا ۱۸۰ نویسه باشد و حداقل ۲۴ ساعت نگه‌داری می‌شود. علاوه بر آن، order_id در محدوده هر فروشگاه یکتا باقی می‌ماند.

محدوده فاکتور و پارامترهای درخواست

amount_tomanعدد صحیح؛ حداقل ۱٬۰۰۰ و حداکثر ۵۰۰٬۰۰۰٬۰۰۰ تومان.
order_idاختیاری، حداکثر ۱۲۰ نویسه؛ در هر فروشگاه نباید تکراری باشد.
descriptionاختیاری، حداکثر ۵۰۰ نویسه.
fee_modeاختیاری؛ merchant، customer، split یا default. مقدار free پذیرفته نمی‌شود.
card_idاختیاری؛ باید شناسه یک کارت فعال متعلق به همان پذیرنده باشد.
callback_urlاختیاری و مخصوص همان فاکتور؛ در صورت حذف، Callback اختصاصی فروشگاه استفاده می‌شود. Callback فروشگاه دیگری یا Callback عمومی حساب به ارث نمی‌رسد.
return_urlاختیاری؛ پس از پرداخت موفق، دکمه بازگشت به فروشگاه در رسید نمایش داده می‌شود.
ttl_minutesاختیاری؛ حداقل ۵ و حداکثر ۱٬۴۴۰ دقیقه. در صورت حذف، مقدار پیش‌فرض سامانه استفاده می‌شود.
unique_amount_rialسامانه به‌طور خودکار ۱ تا ۹۹۹ تومان کد تطبیق به مبلغ نهایی اضافه می‌کند.
حداکثر ۵۰۰ میلیون تومان مربوط به مبلغ پایه فاکتور است. مبلغ نهایی ممکن است به‌اندازه سهم کارمزد مشتری و کد تطبیق یکتا بیشتر باشد.

Rate Limit و سیاست ارسال درخواست

وضعیت دقیق محدودیت در نسخه فعلی

Rate Limit در نسخه {{ app_version }} فعال است. پنجره همه سهمیه‌ها ۶۰ ثانیه است و هر درخواست می‌تواند هم‌زمان در چند سهمیه شمارش شود؛ عبور از هرکدام پاسخ 429 ایجاد می‌کند.
هر API Keyحداکثر ۱۲۰ درخواست در دقیقه روی مجموع مسیرهای /api/v1.
ساخت فاکتورحداکثر ۳۰ درخواست در دقیقه برای POST /api/v1/invoices به‌ازای هر API Key.
هر IPحداکثر ۳۰۰ درخواست در دقیقه روی مجموع مسیرهای /api/v1.
پنجرهFixed Window شصت‌ثانیه‌ای؛ شمارنده در ابتدای پنجره بعدی صفر می‌شود.

هدرهای سهمیه

X-RateLimit-Limitحد سهمیه فعال و محدودکننده‌تر برای همین پاسخ.
X-RateLimit-Remainingتعداد درخواست باقی‌مانده در پنجره جاری.
X-RateLimit-Resetزمان پایان پنجره به‌صورت Unix timestamp.
X-RateLimit-Scopeیکی از ip، api_key یا invoice_create.
Retry-Afterفقط در پاسخ ۴۲۹؛ تعداد ثانیه تا امکان تلاش مجدد.
شمارنده‌ها در دیتابیس اصلی ذخیره می‌شوند. بنابراین Restart و اجرای چند Replica سهمیه را صفر یا چندبرابر نمی‌کند. فقط هش API Key و هویت IP ذخیره می‌شود و پنجره‌های قدیمی خودکار پاک می‌شوند.

Callback نتیجه پرداخت

وبهوک اختصاصی هر فروشگاه با Secret مستقل

پس از تأیید، یک درخواست POST با رویداد invoice.paid به آدرس ثبت‌شده ارسال می‌شود. پاسخ موفق هر کد 2xx است؛ Redirect دنبال نمی‌شود و Timeout هر تلاش ۱۰ ثانیه است. رویداد ابتدا در Outbox دیتابیس ثبت می‌شود و با Restart یا Deploy از بین نمی‌رود.

تلاش اولبلافاصله پس از تأیید پرداخت.
تلاش دوم۳۰ ثانیه پس از شکست تلاش اول.
تلاش سوم۵ دقیقه پس از شکست تلاش دوم.

اعتبارسنجی امضا در Python

import hashlib, hmac, json

def verify_webhook(raw_body: bytes, received_signature: str, secret: str) -> bool:
    payload = json.loads(raw_body)
    canonical = json.dumps(
        payload,
        ensure_ascii=False,
        separators=(",", ":"),
        sort_keys=True,
    ).encode("utf-8")
    expected = hmac.new(secret.encode(), canonical, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received_signature)

وبهوک اختصاصی پیامک بانکی

هر پذیرنده یک URL مستقل و محرمانه دارد

POST{{ sms_webhook_url }}
توکن واقعی عمداً در این صفحه پنهان شده است. URL کامل را فقط از «اتصال و API ← وبهوک پیامک» داخل ربات دریافت کنید. در صورت افشا، همان‌جا گزینه «تعویض توکن امنیتی وبهوک» را بزنید.
نصب برنامه: برای امنیت پیامک‌های بانکی فقط نسخه رسمی ناشر را نصب کنید. دریافت نسخه رسمی SMS Forwarder

بدنه استاندارد SMS Forwarder

{"device_id":"phone-1","sender":"{in-number}","message":"{msg}","received_time":"{time}","incoming_sim":"{in-sim}"}
مهم: متغیرهای {in-number}، {msg}، {time} و {in-sim} را با دکمه {} خود برنامه درج کن. Retry پیام‌های قدیمی ممکن است بدنه ذخیره‌شده قبلی را دوباره ارسال کند.
۱در برنامه SMS Forwarder یک Filter یا Rule برای پیامک‌های بانکی ایجاد کنید.
۲مقصد را Webhook URL و روش ارسال را POST انتخاب کنید.
۳URL کامل وبهوک را از داخل ربات کپی و بدون تغییر وارد کنید؛ نشانی ماسک‌شده این صفحه قابل استفاده نیست.
۴در قسمت Body گزینه JSON را انتخاب و اسکلت JSON بالا را وارد کنید.
۵داخل مقدار sender، گزینه Incoming Number : {in-number} را از فهرست برنامه درج کن.
۶داخل مقدار message، گزینه Message Body : {msg} را از فهرست برنامه درج کن.
۷در صورت نیاز، {time} و {in-sim} را نیز از همان فهرست پویا درج کن.
۸مقدار phone-1 شناسه این گوشی است و برای گوشی‌های دیگر باید متفاوت باشد.
۹فقط یک نوع پیام، ترجیحاً SMS، را برای هر فیلتر فعال کنید تا درخواست تکراری ایجاد نشود.
۱۰نام بانک را دستی وارد نکن؛ سیستم بانک را از فرستنده و متن واقعی پیامک تشخیص می‌دهد.
نمونه JSON برای برنامه‌های دیگر 
{
  "sender": "VARIABLE_FOR_SMS_SENDER",
  "message": "VARIABLE_FOR_SMS_BODY",
  "device_id": "phone-1"
}

نام متغیرها در برنامه‌های مختلف فرق می‌کند. فیلد bank_code اختیاری است و برای اتصال عادی لازم نیست.

فهرست دستگاه‌های مجاز: با GET/PUT /api/v1/account/sms-devices شناسه‌های مجاز مانند phone-1 را مدیریت کنید. پس از تعریف فهرست، پیامک دستگاه ناشناس با خطای SMS_DEVICE_NOT_TRUSTED رد می‌شود.
URL اختصاصی پیامک نقش کلید امنیتی دارد. آن را در کانال، گروه یا کد عمومی منتشر نکنید.

ساختار پاسخ خطاها و وضعیت‌ها

قرارداد فعلی API برای مدیریت خطا در Backend پذیرنده

ساختار استاندارد همه خطاهای JSON

تمام خطاهای مسیرهای /api/ و /webhooks/ با قرارداد ثابت زیر بازگردانده می‌شوند. مقدار request_id در هدر X-Request-ID نیز تکرار می‌شود.

{
  "success": false,
  "error": {
    "code": "INVALID_AMOUNT",
    "message": "مبلغ فاکتور معتبر نیست",
    "field": "amount_toman",
    "details": {
      "min": 1000,
      "max": 500000000
    }
  },
  "request_id": "req_2b8f5c9d14a04f2a9b67c001",
  "timestamp": "2026-08-01T10:20:30Z"
}
فیلدهای field و details ممکن است null باشند، اما خود آن‌ها همیشه در پاسخ وجود دارند. برای منطق برنامه از error.code استفاده کنید و متن message را فقط برای نمایش یا ثبت لاگ در نظر بگیرید.

    "field": "amount_toman",

      "errors": [
        {

کدهای HTTP و error.code قابل انتظار

400BAD_REQUEST یا INVOICE_CREATE_FAILED؛ تنظیم تجاری نامعتبر، کارت فعال‌نبودن، کمبود موجودی کارمزد یا تکمیل ظرفیت مبلغ یکتا.
401INVALID_API_KEY، INVALID_SMS_WEBHOOK_TOKEN یا INVALID_SMS_WEBHOOK_SECRET.
404INVOICE_NOT_FOUND، SMS_WEBHOOK_NOT_FOUND یا NOT_FOUND.
409ORDER_ID_CONFLICT یا INVOICE_NOT_CANCELLABLE.
422VALIDATION_ERROR یا SMS_TEMPLATE_NOT_RESOLVED.
429RATE_LIMITED همراه هدر Retry-After و جزئیات سهمیه.
500/502/503/504INTERNAL_ERROR برای خطای برنامه؛ ۵۰۲ تا ۵۰۴ ممکن است از زیرساخت Railway یا Proxy صادر شوند و قالب آن‌ها خارج از کنترل برنامه باشد.
