احراز هویت API

کلید در هدر همه درخواست‌های خصوصی ارسال می‌شود

HEADERX-API-Key: gw_your_private_key
هر کلید به یک فروشگاه مشخص متصل است. کلید فروشگاه دیگر امکان استعلام یا لغو فاکتورهای این فروشگاه را ندارد. کلید را فقط در Backend نگه دارید.
کلید جداگانه فقط دسترسی‌ها را تفکیک می‌کند و به‌معنای Sandbox نیست. تمام فاکتورهای ساخته‌شده در این نشانی، واقعی هستند.

مقادیر مجاز fee_mode

این فیلد مشخص می‌کند چه مقدار از کارمزد تأیید به مبلغ پرداختی مشتری افزوده شود. کارمزد سرویس در زمان ساخت فاکتور از کیف پول پذیرنده رزرو و پس از پرداخت از همان کیف پول کسر می‌شود.

customerتمام کارمزد به مبلغ مشتری افزوده می‌شود؛ customer_fee_rial = fee_amount_rial.
splitنیمی از کارمزد به مبلغ مشتری افزوده می‌شود؛ customer_fee_rial = floor(fee_amount_rial / 2).
merchantچیزی به مبلغ مشتری افزوده نمی‌شود و پذیرنده تمام هزینه را از کیف پول می‌پردازد.
null / حذف فیلدسیاست کارمزد ثبت‌شده برای حساب پذیرنده استفاده می‌شود.
اگر مبلغ کارمزد حساب روی صفر باشد، سرویس رایگان است؛ چیزی رزرو یا کسر نمی‌شود و انتخاب fee_mode اثر مالی ندارد.
payable_amount_rial = base_amount_rial + customer_fee_rial + unique_amount_rial

Rate Limit و سیاست ارسال درخواست

وضعیت دقیق محدودیت در نسخه فعلی

نسخه 0.5.2 محدودیت ثابت در سطح برنامه اعمال نمی‌کند. در نتیجه هدرهای X-RateLimit-Limit، X-RateLimit-Remaining و Retry-After توسط خود بلوپی تولید نمی‌شوند و پاسخ 429 جزو قرارداد فعلی برنامه نیست.

بااین‌حال، Railway، پراکسی یا لایه شبکه ممکن است مستقل از برنامه درخواست را محدود یا قطع کند. کلاینت باید خطاهای شبکه، 429 زیرساخت و خطاهای موقت 5xx را مدیریت کند.

POST /invoicesتلاش خودکار کورکورانه توصیه نمی‌شود. برای هر سفارش یک order_id پایدار بفرستید تا ساخت تکراری با پاسخ ۴۰۹ مشخص شود.
GET /invoices/{id}برای استعلام می‌توان از Backoff تدریجی استفاده کرد و از Polling بسیار سریع پرهیز کرد.
Timeout پیشنهادیبرای درخواست API حداقل ۱۵ ثانیه در نظر بگیرید.
نبود Rate Limit داخلی به معنی تضمین ظرفیت نامحدود نیست. در نسخه‌ای که محدودیت رسمی اضافه شود، عددها و هدرهای آن باید به‌عنوان تغییر قرارداد API اعلام شوند.

محیط Sandbox

تفکیک تست از پرداخت واقعی

در نسخه 0.5.2 محیط Sandbox مستقل وجود ندارد. آدرس API، صفحه پرداخت، کارت مقصد و تطبیق پیامک همگی به محیط واقعی متصل‌اند.

ساخت «فروشگاه آزمایشی» یا «کلید API تست» فقط دسترسی و گزارش‌ها را جدا می‌کند؛ فاکتور ساخته‌شده همچنان واقعی است و واریز بانکی واقعی می‌تواند آن را تأیید کند.

webhook.testاز داخل ربات قابل ارسال است و بدون پرداخت واقعی فقط اتصال Callback و امضا را آزمایش می‌کند.
فاکتور تستبرای آزمایش انتها‌به‌انتها از فروشگاه، کلید و کارت جدا و حداقل مبلغ ۱٬۰۰۰ تومان استفاده کنید؛ وجه واقعی جابه‌جا می‌شود.
کارت/پیامک جعلیپشتیبانی نمی‌شود و نباید به وبهوک محیط واقعی ارسال شود.

Callback نتیجه پرداخت

وبهوک اختصاصی هر فروشگاه با Secret مستقل

پس از تأیید، یک درخواست POST با رویداد invoice.paid به آدرس ثبت‌شده ارسال می‌شود. پاسخ موفق هر کد 2xx است؛ Redirect دنبال نمی‌شود و Timeout هر تلاش ۱۲ ثانیه است.

تلاش اولبلافاصله پس از تأیید پرداخت.
تلاش دوم۲ ثانیه پس از پایان تلاش اول.
تلاش سوم۶ ثانیه پس از پایان تلاش دوم؛ در پاسخ‌های سریع تقریباً ۸ ثانیه پس از شروع تلاش اول.
Callback آزمایشیفقط یک بار ارسال می‌شود و Retry ندارد.
شناسه X-Gateway-Delivery، امضا و Timestamp در سه تلاش یک رویداد ثابت می‌مانند. زمان واقعی کل فرایند با توجه به تأخیر سرور مقصد می‌تواند بیشتر از ۸ ثانیه باشد.

اعتبارسنجی امضا در Python

import hashlib, hmac, json

def verify_webhook(raw_body: bytes, received_signature: str, secret: str) -> bool:
    payload = json.loads(raw_body)
    canonical = json.dumps(
        payload,
        ensure_ascii=False,
        separators=(",", ":"),
        sort_keys=True,
    ).encode("utf-8")
    expected = hmac.new(secret.encode(), canonical, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received_signature)

اعتبارسنجی امضا در PHP

<?php
$secret = 'SECRET_FROM_BOT';
$raw = file_get_contents('php://input');
$payload = json_decode($raw, true);
ksort($payload);
$canonical = json_encode($payload, JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES);
$expected = hash_hmac('sha256', $canonical, $secret);
$received = $_SERVER['HTTP_X_GATEWAY_SIGNATURE'] ?? '';
if (!hash_equals($expected, $received)) {
    http_response_code(401);
    exit('invalid signature');
}
http_response_code(200);
echo 'ok';

وبهوک اختصاصی پیامک بانکی

هر پذیرنده یک URL مستقل و محرمانه دارد

POST{{ sms_webhook_url }}

بدنه استاندارد SMS Forwarder

{"device_id":"phone-1","sender":"{in-number}","message":"{msg}","received_time":"{time}","incoming_sim":"{in-sim}"}
مهم: متغیرهای {in-number}، {msg}، {time} و {in-sim} را با دکمه {} خود برنامه درج کن. Retry پیام‌های قدیمی ممکن است بدنه ذخیره‌شده قبلی را دوباره ارسال کند.
۱در برنامه SMS Forwarder یک Filter یا Rule برای پیامک‌های بانکی ایجاد کنید.
۲مقصد را Webhook URL و روش ارسال را POST انتخاب کنید.
۳Webhook اختصاصی بالا را بدون تغییر وارد کنید.
۴در قسمت Body گزینه JSON را انتخاب و اسکلت JSON بالا را وارد کنید.
۵داخل مقدار sender، گزینه Incoming Number : {in-number} را از فهرست برنامه درج کن.
۶داخل مقدار message، گزینه Message Body : {msg} را از فهرست برنامه درج کن.
۷در صورت نیاز، {time} و {in-sim} را نیز از همان فهرست پویا درج کن.
۸مقدار phone-1 شناسه این گوشی است و برای گوشی‌های دیگر باید متفاوت باشد.
۹فقط یک نوع پیام، ترجیحاً SMS، را برای هر فیلتر فعال کنید تا درخواست تکراری ایجاد نشود.
۱۰نام بانک را دستی وارد نکن؛ سیستم بانک را از فرستنده و متن واقعی پیامک تشخیص می‌دهد.
نمونه JSON برای برنامه‌های دیگر 
{
  "sender": "VARIABLE_FOR_SMS_SENDER",
  "message": "VARIABLE_FOR_SMS_BODY",
  "device_id": "phone-1"
}

نام متغیرها در برنامه‌های مختلف فرق می‌کند. فیلد bank_code اختیاری است و برای اتصال عادی لازم نیست.

URL اختصاصی پیامک نقش کلید امنیتی دارد. آن را در کانال، گروه یا کد عمومی منتشر نکنید.

خطاهای تجاری و احراز هویت

بیشتر خطاهای API خصوصی با ساختار استاندارد FastAPI بازگردانده می‌شوند. در این پاسخ‌ها فیلد success وجود ندارد.

متن و فیلدهای جزئی خطای ۴۲۲ توسط نسخه Pydantic/FastAPI ساخته می‌شوند؛ برای تصمیم‌گیری برنامه‌ای، بیشتر به Status Code و مسیر loc تکیه کنید.

کدهای HTTP قابل انتظار

400خطای تجاری یا تنظیم نامعتبر؛ مانند Callback غیرمجاز، کارت فعال‌نبودن، کمبود موجودی کارمزد یا تکمیل ظرفیت مبلغ‌های یکتا.
401API Key، Webhook token یا Secret نامعتبر/غیرفعال.
404فاکتور، مستندات اختصاصی یا Webhook موردنظر پیدا نشد یا به فروشگاه این کلید تعلق ندارد.
409order_id تکراری یا عملیات ناسازگار با وضعیت فعلی فاکتور؛ مانند لغو فاکتور پرداخت‌شده.
422ساختار یا مقدار ورودی با Schema سازگار نیست؛ یا بدنه SMS Forwarder هنوز شامل Placeholder است.
429در برنامه فعلی تولید نمی‌شود؛ ممکن است از لایه زیرساخت دریافت شود.
500/502/503/504خطای داخلی یا موقت زیرساخت؛ درخواست ساخت فاکتور را بدون بررسی نتیجه قبلی تکرار نکنید.

وضعیت‌های فاکتور

pendingدر انتظار واریز و تأیید پیامک.
paidپرداخت قطعی شده است؛ ارسال Callback جداگانه انجام می‌شود و موفقیت آن وضعیت فاکتور را تغییر نمی‌دهد.
expiredمهلت پرداخت تمام شده و رزرو کارمزد/مبلغ آزاد شده است.
cancelledفاکتور در حالت انتظار توسط پذیرنده لغو شده است.
